# v1.2.2 課程紀錄費率核對

根因：舊資料匯入時，學生與固定課表的費率為 0。學生後續已調整學費，但舊課程仍保留 estimated_fee=0；日課表簽到原先直接送出該值，因費率欄位不顯示，使用者無從發現。

修正分成兩部分：

- 未來從固定課表簽到，若原課程費率是 0、非補課，則預設取該學生目前學費。後端拒絕舊客戶端繼續送出符合舊零元課表條件的 0 元簽到，提示重新整理。一般非零費率、補課與單堂簽到維持原行為；既有請求重試仍先比對原始簽到。
- 新增 `lesson_records` 唯讀視圖。只有原簽到費率、課程費率、固定課表費率都為 0，非補課，且簽到前的最新學費異動是正值、先前確有零元紀錄時，才依該次簽到建立時間的歷史費率顯示核對值。其餘保持原始簽到值。日後調價不會回溯改變這個核對值。

學生資料夾、簽到詳細資料、授課統計與未來產生的學費草稿均使用相同核對口徑；畫面標示來源及原始金額。原始 lessons.fee、簽名圖片、已正式開立的學費袋明細與實際收款均不修改。視圖不含簽名圖片，採 security_invoker 並沿用來源表 RLS，只授權 authenticated SELECT；匿名與未核准帳號不可讀取。

正式 migration 已由 Supabase 工具套用為 `20261101025926_legacy_lesson_fee`。檔名對齊正式紀錄，不改寫 migration 歷史。驗證前後 students、fee_changes、lessons、課表與所有帳務資料指紋一致；兩筆符合此匯入缺陷的正式紀錄已可讀出簽到當時的正確費率。

驗證：59 項資料庫／邏輯回歸、28 項瀏覽器回歸、TypeScript／Vite 建置通過。新增測試涵蓋原資料不變、歷史費率固定、列表與詳情及報表一致、草稿計費一致、舊客戶端零元防護、重試、合法零元課程與權限拒絕。

部署順序：先套用上述 migration，再部署 v1.2.2 前端。前端回退可保留此向後相容的唯讀投影與防護；沒有真實帳務資料回填需要撤銷。舊客戶端若遇到零元費率警示，重新整理即可。
