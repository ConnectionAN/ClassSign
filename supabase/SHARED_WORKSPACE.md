# 單一工作室共用帳號

2026-10-31 使用者確認：所有已授權帳號共用查看與管理同一份學生、課表、簽到及統計。

`teacher_access` 仍是帳號授權清單；新註冊或 Google 登入不會自行取得資格。此變更不修改登入流程、Auth 設定或現有 Google 帳號連結。

增量 `20261031082429_shared_workspace.sql` 將既有唯一資料所有者固定為工作室的資料歸屬，儲存於不對外開放的 `studio_private.workspace_settings`。學生、簽名與歷史資料的 owner 不改寫；所有已授權帳號經 `studio_owner()` 解析到同一資料歸屬，RLS 及 RPC 使用同一範圍與交易鎖。共用帳號可以新增學生、調價、封存、排課、請假、調課、雙簽及作廢；無直接寫表權限。

`teacher_access` 本身仍只讀取自己的授權列，前端不會因多帳號而收到多列。撤銷其中一個帳號不會改變共用資料所有者，其他已授權帳號可繼續管理。課務異動新增 `actor` 欄位記錄實際操作帳號；原有歷史保持空值，不推測過去操作人。

空白新安裝會在第一個帳號被加入授權清單時初始化工作室。這不是多工作室系統：若既有學生分屬多個 owner，遷移會停止，需先審查，不會自行搬移或合併資料。

部署前備份全部業務表、函式及政策，核對仍只有一個資料 owner，再套用此增量（不可重跑001或課表初始化）。以兩個授權身分驗證共用讀寫、費率快照、簽到防重與撤權；測試異動須rollback。安全顧問可能提示 `studio_owner()` 是可供登入者呼叫的 SECURITY DEFINER 讀取函式；它只有在呼叫者位於授權清單時才回傳固定資料歸屬，未授權者回傳NULL。

`database.test.mjs` 與 `schedule.test.mjs` 保留在歷史遷移階段驗證當時的隔離規則；`shared-workspace.test.mjs` 執行完整遷移並驗證新的共用契約、未授權拒絕、不可直接寫表、原紀錄保留及空白安裝。
